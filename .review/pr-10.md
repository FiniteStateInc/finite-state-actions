# PR #10 — fix(wait): replace the bash composite with a node24 action

## PR description

## What this changes

`actions/wait` was a composite action whose one step declared `shell: bash`. On a Windows runner GitHub resolves that to Git Bash. That is fine on GitHub-hosted `windows-*` images, which ship Git for Windows, but on a self-hosted Windows runner without it the step fails before `wait.sh` ever runs — with GitHub's own "bash not found" error, not one of our `::error::` annotations.

This makes `wait` the eighth bundled `node24` action. It invokes fs-cli through `@actions/exec` with an argument list and no shell, so one implementation covers ubuntu, macOS, and Windows.

The alternative was a `wait.ps1` alongside `wait.sh`, branching on `runner.os`. That is a smaller diff today and a permanent tax: the timeout parsing, the token masking, and every error message would exist twice and have to be changed twice.

**The fs-cli call is unchanged** — `query --type scan --format json --endpoint https://<domain> --version-id <id> --wait --fail-on-scan-incomplete`, token passed via `FS_TOKEN` so it stays out of argv. Inputs and their defaults are unchanged. There are still no outputs; the exit code is the verdict.

## Behaviour changes

Four, all deliberate:

- **`wait` now installs fs-cli when it has to.** It goes through `ensureFsCli`, like `scan` and `upload`. Previously it ran `command -v fs-cli` and failed with "fs-cli not found" if no earlier step had installed one. It also now validates the executable header of an fs-cli found on `PATH` and re-downloads a foreign binary, where the shell version trusted whatever was there. `setup`/`scan`/`upload` first is still the normal path; `wait` alone in a job with an `api-token` and a `version-id` now works too.
- **A failure exits 1, whatever fs-cli returned.** The shell version ended with `exit "$QUERY_EXIT"`, so the step's process carried fs-cli's own code; a Node action reports failure through `core.setFailed`, which exits 1. No workflow expression can read a step's numeric exit code either way — `wait` has no `exit-code` output and never had one — so this is visible only to log tooling that scrapes runner output. The code fs-cli returned is now in the failure message instead: `fs-cli query exited 3 for version ver-999 on app.finitestate.io`.
- **The titled `::error::` annotations are gone.** `wait.sh` wrote `::error title=Scan did not finish::`; `core.setFailed` writes an untitled `::error::`. Anything matching the old titles (`No version ID`, `No API token`, `Scan did not finish`) needs updating — the new strings are `No version to wait on.`, `FINITE_STATE_AUTH_TOKEN is not set.`, and the `fs-cli query exited N` message above. `.claude/skills/fs-github-actions/SKILL.md` is updated for the first of those.
- **`timeout` is parsed by shared code.** `parseTimeoutMinutes` in `packages/core/src/timeout.ts`, extracted from `upload`, which had the same 20 lines inline. Same rejections (`600s`, `10 minutes`, `-5`, `0`), same rounding warning, in both actions.

## Deleted

`wait.sh`, `__tests__/action.test.sh`, and the `wait-action` CI job. The two bash traps that job existed to cover went with them, since neither is reachable from TypeScript:

- The guarded empty-array expansion — under `set -u` an empty array expansion is an error in bash 3.2, which is what macOS ships.
- The base-10 forcing around the timeout — bash reads a leading zero as octal, so `timeout: 0600` waited 7 minutes and `09` aborted the script outright.

## Windows coverage

The `test` job in `.github/workflows/ci.yml` is now a matrix over `ubuntu-latest`, `macos-latest`, and `windows-latest`, so all 218 tests across every package run on each OS the actions support. `lint`, `typecheck`, and `build` stay on ubuntu — they produce identical results anywhere.

`actions/wait/__tests__/main.test.ts` adds 24 tests. Three groups pin the properties that let one implementation be portable:

- it runs exactly the binary path `ensureFsCli` returns — checked for four paths, including `D:\a\_temp\fs-cli\fs-cli.exe` and `C:\Program Files\fs-cli\fs-cli.exe`, by parsing the command line back with `@actions/exec`'s own `argStringToArray` rather than by reading the exec mock;
- it passes an argument list and gives exec only `env` and `ignoreReturnCode`, asserted as an exact key set, so no `shell` or `windowsVerbatimArguments` can appear and argument quoting cannot differ between runners;
- it calls `ensureFsCli` rather than assuming `PATH` resolves a bare name.

`packages/core/__tests__/install-cli.test.ts` adds three `ensureFsCli` cases with `process.platform` stubbed to `win32`, so the `['.exe', '.cmd', '']` branch of `findOnPath` — on `wait`'s critical path now — is exercised on every leg of the matrix rather than only the Windows one. `packages/core/__tests__/timeout.test.ts` and `exec-path.test.ts` are new: both helpers are exported from `@finite-state/core` and had no test in the package that owns them.

The rest cover the version fallback, the token staying out of argv, the non-zero exit message, and the timeout parsing — including `0600`, which the bash version read as octal 384 and this one reads as 600 seconds, or 10 minutes.

## Also in this PR

Three things the `wait` rewrite turned up, fixed here rather than left for a follow-up:

- **`exec` splits its first parameter on spaces, even when an args array is passed.** `@actions/exec`'s `exec()` runs the command line through its own `argStringToArray` before spawning, so an fs-cli at `C:\Program Files\fs-cli\fs-cli.exe` was run as `C:\Program` with the rest prepended to the arguments, failing with a spawn error naming a path nobody wrote. `packages/core/src/exec-path.ts` adds `quoteExecPath`, and `scan`, `upload` and `wait` — the three actions that run a binary path they did not choose — all go through it. `run-report` runs `pipx` and `fs-report` by bare name and is unaffected.
- **`actions/upload-scan/action.yml` still declared `shell: bash`** for its deprecation notice, which is the failure this PR exists to remove. The notice now rides on the required `type` input's `deprecationMessage`, which GitHub logs itself on every runner OS, and the composite is one `uses:` step with no `run:` step and no shell.
- **The `build` job's dist check used `git diff`, which reports nothing for untracked files.** The root `.gitignore` lists `dist/` and `*.js`, so a new action's bundle starts out untracked: an action could ship with no `dist/index.js` and a green build. It is now `git status --porcelain --ignored=matching actions/*/dist/`.

+import * as core from '@actions/core'
+import * as exec from '@actions/exec'
+import {
+  FsClient,
+  ensureFsCli,
+  quoteExecPath,
+  readSetupContext,
+  timeoutSecondsToMinutes,
+} from '@finite-state/core'
+
+/**
+ * A failure this action raises itself, carrying the annotation title the shell
+ * version used and the code to exit with.
+ *
+ * The titles are the ones `wait.sh` wrote, so a log filter or dashboard keyed
+ * on `title=No version ID` keeps matching. `exitCode` is fs-cli's own for a
+ * scan that did not finish, which the shell version passed through with
+ * `exit "$QUERY_EXIT"`.
+ */
+class WaitFailure extends Error {
+  constructor(
+    message: string,
+    readonly title: string,
+    readonly exitCode = 1,
+  ) {
+    super(message)
+  }
+}
+
+/**
+ * Runs `read`, re-raising whatever it throws under `title`. Awaits, so an
+ * async `read` rejecting is titled too rather than slipping past as a plain
+ * error.
+ */
+async function titled<T>(title: string, read: () => T | Promise<T>): Promise<T> {
+  try {
+    return await read()
+  } catch (err) {
+    throw new WaitFailure(err instanceof Error ? err.message : String(err), title)
+  }
+}
+
+export async function run(): Promise<void> {
+  try {
+    // ── Read inputs ──────────────────────────────────────────────────────────
+    const apiTokenOverride = core.getInput('api-token') || undefined
+    const domainOverride = core.getInput('domain') || undefined
+    const versionIdInput = core.getInput('version-id') || undefined
+
+    // ── Read setup context, falling back to this action's own inputs ─────────
+    // Running without setup, scan or upload is supported: pass api-token here.
+    // Read before the timeout is parsed so a job missing its token fails on
+    // the token, not on whichever other input also happens to be wrong.
+    const ctx = await titled('No API token', () =>
+      readSetupContext({
+        apiToken: apiTokenOverride,
+        domain: domainOverride,
+        versionId: versionIdInput,
+      }),
+    )
+
+    // Masks a token that came from this action's input rather than setup, where
+    // it is masked already. First thing after the read, so nothing below can
+    // log it unmasked.
+    core.setSecret(ctx.apiToken)
+
+    if (!ctx.versionId) {
+      throw new WaitFailure(
+        'No version to wait on. Run scan or upload first, or pass version-id. It is the ' +
+          "platform's version ID, not a label like v1.2.3.",
+        'No version ID',
+      )
+    }
+
+    // Unset leaves fs-cli its own 30-minute default.
+    const timeout = await titled('Bad timeout', () =>
+      timeoutSecondsToMinutes(core.getInput('timeout')),
+    )
+    if (timeout.warning) {
+      core.warning(timeout.warning, { title: 'Timeout rounded' })
+    }
+
+    // Reuses an fs-cli that setup, scan or upload already put on PATH and
+    // downloads one only when this is the first Finite State step in the job.
+    const fsCli = await titled('fs-cli not found', () =>
+      ensureFsCli(new FsClient({ apiToken: ctx.apiToken, domain: ctx.domain })),
+    )
+
+    core.info(`Waiting for scans on version ${ctx.versionId} to finish.`)
+
+    // --wait polls; --fail-on-scan-incomplete fails the step on a failed scan,
+    // a poll timeout, or a version with no scans at all, so a later step never
+    // reads partial results from a green job.
+    //
+    // fs-cli's exit code is the verdict, which is what upload treats as
+    // authoritative too. upload additionally parses the JSON rollup only
+    // because it publishes a scan-status output that must not contradict the
+    // exit code; this action has no such output and so has nothing to parse.
+    //

+/**
+ * Quotes a binary path for the first parameter of `@actions/exec`'s `exec`.
+ *
+ * `exec` runs that parameter through its own `argStringToArray` even when an
+ * args array is passed, so a bare path splits on spaces: fs-cli at
+ * `C:\Program Files\fs-cli\fs-cli.exe` is run as `C:\Program` with
+ * `Files\fs-cli\fs-cli.exe` prepended to the arguments, and the step fails with
+ * a spawn error naming a path nobody wrote.
+ *
+ * Inside double quotes that parser keeps a lone backslash as-is, treats `\\` as
+ * one backslash, and `\"` as a literal quote — so only a backslash run at the
+ * end of the path (which would otherwise escape the closing quote) and an
+ * embedded quote need escaping.
+ *
+ * Shared by every action that runs a binary whose path it did not choose (one
+ * under `RUNNER_TEMP`, or one found on `PATH`) so the quoting cannot be right
+ * in one action and missing in the next.
+ */
+export function quoteExecPath(binary: string): string {
+  const escaped = binary
+    .replace(/"/g, '\\"')
+    // Doubled so the closing quote is not escaped by them.
+    .replace(/\\+$/, (backslashes) => backslashes + backslashes)
+
+  return `"${escaped}"`
+}

+/**
+ * Turns a `timeout` input in seconds into the whole minutes fs-cli accepts,
+ * with the annotation to emit when that conversion is not exact.
+ *
+ * `minutes` is undefined for an empty input, which leaves fs-cli its own
+ * 30-minute default rather than a bound this action invented. Shared by every
+ * action with a `timeout` input so the parsing, the rejections, and the
+ * rounding cannot drift apart between them.
+ *
+ * Returns the rounding message rather than writing it, so the caller titles it
+ * and core stays usable without the Actions logging channel.
+ */
+export function timeoutSecondsToMinutes(input: string | undefined): {
+  minutes?: number
+  warning?: string
+} {
+  const timeout = (input ?? '').trim()
+  if (!timeout) {
+    return {}
+  }
+
+  // Deliberately strict: parseInt would read "600s" as 600 and "10 minutes" as
+  // 10, quietly applying a bound the caller did not ask for. A leading zero is
+  // base 10 here, where the bash implementation this replaced read "0600" as
+  // octal 384 and aborted outright on "09".
+  if (!/^\d+$/.test(timeout)) {
+    throw new Error(
+      `timeout must be a whole number of seconds, got "${timeout}". ` +
+        `Leave it unset to use fs-cli's own default.`,
+    )
+  }
+
+  const seconds = parseInt(timeout, 10)
+  if (seconds <= 0) {
+    throw new Error(`timeout must be a positive number of seconds, got "${timeout}".`)
+  }
+
+  const minutes = Math.max(1, Math.ceil(seconds / 60))
+  // fs-cli takes whole minutes, so anything that is not an exact multiple of 60
+  // rounds up — say which bound will actually apply rather than waiting longer
+  // than asked without mentioning it.
+  if (seconds % 60 !== 0) {
+    return {
+      minutes,
+      warning:
+        `timeout ${seconds}s is not a whole number of minutes, which is all fs-cli accepts; ` +
+        `rounding up to ${minutes} minute(s).`,
+    }
+  }
+
+  return { minutes }
+}
